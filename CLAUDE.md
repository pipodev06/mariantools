# MarianTools

Suite de herramientas (OCR, PDF, imagen, texto, etc.). Ver `tools.md` para catálogo completo.

## Stack
- Vite + React 19 + TypeScript
- Tailwind CSS v4 (import directo, sin `tailwind.config`)
- react-router-dom v7
- @tabler/icons-react — íconos, ver lista curada abajo
- `vercel.json` — rewrite catch-all (`/(.*) → /index.html`) para que rutas hijas de React Router (ej. `/ocr`) no den 404 al refrescar en Vercel. No afecta `/api/*`: Vercel prioriza funciones/archivos reales sobre los rewrites.

## Copy / idioma

Español neutro tipo Perú (PE) — **nunca voseo argentino**. "transcribe" no "transcribí", "genera" no "generá", "crea"/"lee" no "creá"/"leé", etc. Usar conjugación de tercera persona/imperativo neutro, no vos. Aplica a todo texto de UI (`tools.ts`, páginas, componentes). `tools.md` es documento de planificación del usuario, no se toca.

## Tipografía

Fuente principal: **Comfortaa**, self-hosted (no Google Fonts CDN) desde `src/assets/fonts/comfortaa/*.ttf`, declarada vía `@font-face` en `src/index.css` y seteada como `--font-sans` (Tailwind v4 la propaga a `html`/body vía preflight, sin tocar `App.tsx`). Solo se guardan los 3 pesos que realmente se usan en el código — `Regular`(400) para texto normal, `SemiBold`(600) para `font-semibold`, `Bold`(700) para `font-bold`. `Light` y `Medium` se borraron por no usarse. Si se necesita un peso nuevo, agregar el `.ttf` a esa carpeta + su `@font-face` correspondiente (no reintroducir el import de Google Fonts).

**Sin monospace, en ningún lado** (pedido explícito del usuario, 2026-08-14): ni `font-mono` ni el `<code>` semántico (que Tailwind v4 preflight pone en monospace por default) — Comfortaa es la única familia tipográfica de todo el sitio, incluso para contraseñas y strings base64. Usar `<span>`/`<p>` en vez de `<code>` para mostrar ese tipo de texto, y `break-all` (no `font-mono`) para que quiebre línea. Corregido retroactivamente en `Contrasenas.tsx` e `ImagenABase64.tsx`, que sí usaban `font-mono` — si aparece un caso nuevo, sacarlo también.

## Estilo/diseño

`App.tsx` sin `className` por pedido explícito del usuario — HTML plano, sin Tailwind. No agregar clases ahí salvo que el usuario lo pida de nuevo. `Header.tsx` y `Footer.tsx` salen de esta regla (pedidos explícitos posteriores de estilarlos).

Escala tipográfica (congelada, normalizada — solo pasos estándar de Tailwind, nada arbitrario tipo `text-[Npx]`): `text-xs`(12) `text-sm`(14) `text-base`(16) `text-lg`(18) `text-xl`(20) `text-2xl`(24) `text-3xl`(30) `text-4xl`(36) `text-5xl`(48). Uso: hero H1 `4xl→5xl`, subtítulo de sección `2xl→3xl`, marca de Header / título de card `lg`, párrafo de hero `lg`, descripción de card `base`, nav/footer/CTA `sm`, cinta "Pronto" `xs`.

- Header: **sticky** (`sticky top-0 z-50`), `border-b border-slate-200 dark:border-slate-800 bg-white dark:bg-slate-900`, contenedor `mx-auto max-w-5xl flex items-center justify-between px-6 py-4`, marca `slate-800`/`slate-100` (no acento), nav link `slate-500` con `hover:text-emerald-600`.

- Card/hero: **glassmorphism** (elegido por el usuario entre glassmorphism vs. blur decorativo) — `bg-white/60 dark:bg-slate-800/40 backdrop-blur-md border border-white/40 dark:border-slate-700/40`, con gradiente decorativo detrás (`bg-linear-to-br from-emerald-200/40 via-transparent to-slate-200/40` (Tailwind v4 renombró `bg-gradient-to-*` → `bg-linear-to-*`, usar siempre la sintaxis nueva), posicionado `absolute inset-0 -z-10` dentro de un contenedor `relative overflow-hidden`). ## Motion / accesibilidad (congelado, introducido 2026-07-16 vía skill `frontend-design`)

- **Keyframes compartidos** en `src/index.css` (fuera de `@theme`, Tailwind v4 no genera `@keyframes` custom desde utilidades arbitrarias): `reveal-up` (fade + translateY 10px, entrada de elementos), `scan-sweep` (barrido vertical `top` 4%→88%, usado en el visual de firma del hero), `fade-in` (backdrop de modal) y `modal-pop` (fade + scale 0.96→1 + translateY, panel de modal). Si se necesita una animación nueva reusable, agregar el `@keyframes` ahí, no inline por componente.
- **Entrada escalonada de grids/listas** (tool cards, resultados de OCR): cada item envuelto en un wrapper con `motion-safe:opacity-0 motion-safe:animate-[reveal-up_0.5s_ease-out_forwards]` + `style={{ animationDelay: '${Math.min(i * 60, 300)}ms' }}` (el `Math.min` evita colas largas en grids con muchos items, ver `upcomingTools` con delay `i * 40` tope `320ms`). **Siempre con prefijo `motion-safe:`** en la clase de opacity Y en la de animate — nunca `opacity-0` a secas, porque si el usuario tiene `prefers-reduced-motion: reduce` la animación no corre y el elemento queda invisible para siempre. Este patrón es el estándar para cualquier grid/lista nueva que aparezca al montar la página.
- **Modal/preview overlay**: backdrop con `motion-safe:animate-[fade-in_0.15s_ease-out]`, panel con `motion-safe:animate-[modal-pop_0.18s_ease-out]`. Aplicar a cualquier modal nuevo que se abra sobre la página (no solo el preview de imagen de OCR).
- **Signature visual del hero (Inicio)**: mini card con línea `scan-sweep` (emerald, `motion-safe:animate-[scan-sweep_2.6s_ease-in-out_infinite]`) sobre barras `slate-300/70` simulando líneas de texto, una barra en `emerald-400/80` representando la línea "reconocida" — motivo ligado al producto (OCR), no decorativo genérico. Es específico del hero de Inicio, no reusar tal cual en otras páginas sin pedirlo; el criterio de motion (`motion-safe:`, timing, keyframes compartidos) sí es el estándar a seguir.
- **Foco visible**: todo elemento interactivo (botón, link, input, textarea) lleva anillo de foco en el acento de marca — `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-emerald-500 focus-visible:ring-offset-2 dark:focus-visible:ring-offset-slate-900` (ajustar el color de `ring-offset` al fondo real del elemento si no es `slate-900`/blanco). En páginas con muchos controles repetidos (ej. `Ocr.tsx`) se define una constante `FOCUS_RING` al tope del archivo y se concatena a cada `className`, en vez de repetir la cadena literal. Reemplaza el outline azul default del navegador — no dejar ningún elemento clickeable sin este anillo.
- **Dropzone con estado de drag-over**: al arrastrar un archivo sobre la zona, cambia a `border-emerald-600 bg-emerald-50/60 dark:bg-emerald-500/10` + ícono en acento + copy cambia a "Suelta las imágenes aquí" (en vez del texto de instrucción). Implementado con contador de `dragCounter` (`useRef`) en `onDragEnter`/`onDragLeave` para evitar parpadeo cuando el cursor pasa sobre elementos hijos del dropzone. Patrón a reusar en cualquier dropzone futura.

## Páginas de herramientas

- **Ruta**: cada tool disponible tiene su página en `src/pages/<Nombre>.tsx` + su `<Route path="...">` en `App.tsx`, coincidiendo con el `href` de `src/data/tools.ts`.
- **`Ocr.tsx`** (`/ocr`) — página de referencia para futuras tools, mismo patrón a seguir:
  - Layout de 2 columnas **iguales y fluidas** (`grid grid-cols-1 lg:grid-cols-2`, 50/50 automático según el ancho del contenedor — no hay track fijo en px; solo aplica el grid de 2 columnas cuando hay archivos, si no, todo a 1 columna): **columna izquierda** = selector de motor (`fast` = Tesseract / `ai` = Mistral Pixtral, 2 cards clickeables lado a lado, borde `emerald-600` si está seleccionado) + dropzone, apilados. **Columna derecha** = solo la lista de archivos.
  - Dropzone: click, drag & drop y pegar (Ctrl+V), `border-dashed`, acepta `image/jpeg`, `image/png`, `image/webp` (`ACCEPTED_TYPES`/`ACCEPTED_EXT` al tope del archivo — al sumar formato nuevo, actualizar ambas). Cada archivo agregado genera su `previewUrl` (`URL.createObjectURL`) al toque, no recién al convertir — se necesita para el thumbnail de la lista.
  - Lista de archivos (columna derecha): cada item = thumbnail clickeable (abre el mismo modal de preview) + nombre + peso (`formatFileSize`, KB si <1MB, si no MB) + botón quitar (`IconX`, revoca el `previewUrl`). Altura **exacta** (no "stretch" aproximado): ambas columnas usan `lg:h-[26rem]` fijo (columna izquierda y contenedor de la lista), con scroll interno (`overflow-y-auto`) en el `<ul>` una vez que el contenido supera esa altura — a ojo entran ~6 items antes de scrollear (asumiendo columnas ~50/50 en un contenedor `7xl`; con `grid-cols-2` fluido esto varía un poco según el ancho real). En mobile, tope fijo `max-h-80` (no hay columna izquierda con la que igualar).
  - Contenedor de la página (`<section>`, normalmente `max-w-7xl`): pasa a `max-w-[90rem]` cuando hay archivos cargados (`files.length > 0`), para que el layout de 2 columnas tenga más aire. Vuelve a `max-w-7xl` en el estado inicial sin archivos. **Ancho en reposo subido de `max-w-5xl` a `max-w-7xl` el 2026-08-17** (junto con Base64/Comparador/Paleta/Facturas) para que el título quede alineado con la grilla de `Otras herramientas` de abajo, que siempre usa `max-w-7xl` — con `max-w-5xl` el título arrancaba 128px más a la derecha que esa grilla, detectado por el usuario comparando screenshots de `/contrasenas` vs `/ocr`. Ver sección `## Ancho de contenedor` más abajo.
  - Botón "Convertir" (`bg-emerald-600`, deshabilitado sin archivos).
  - **Flujo de dos pantallas**: selector de motor + dropzone + lista de archivos + botón Convertir se ocultan por completo una vez que hay `results` (no conviven con la vista de resultados). La vista de resultados muestra primero un botón "Volver a empezar" (`IconRefresh`) que resetea `files`/`results` y revoca los `previewUrl`, y debajo la lista de resultados.
  - Resultado por archivo: fila superior con thumbnail clickeable (`h-14 w-14`, abre modal de vista previa a pantalla completa) + nombre del archivo + **badge de confianza** (solo si `engine === 'fast'`, Mistral no da confidence real) + botones reintentar/copiar/descargar; debajo `textarea` editable con el texto reconocido. Copiar tiene confirmación visual (ícono cambia a `IconCheck` 1.5s).
  - `FileResult` guarda `confidence` y `engine` además de `text`/`previewUrl`/`file` — necesarios para el badge y para saber con qué motor reintentar.
  - **Badge de confianza** (`getConfidenceLevel`, umbrales 80/50): alta `emerald-100/emerald-700`, media `amber-100/amber-700`, baja `red-100/red-700`. Es una excepción puntual a la paleta Emerald+Slate — semáforo de estado (bueno/regular/malo) necesita 3 colores distinguibles, no es un acento de marca. Si se prefiere no usar amber/red aquí tampoco, avisar para ajustarlo.
  - **Reintentar con el otro motor** (`retryResult`, botón `IconSwitchHorizontal` por card, junto a copiar/descargar): reprocesa un único archivo con el motor contrario al que se usó (`fast↔ai`), sin rehacer toda la tanda. Estado `retryingIndex` deshabilita ese botón puntual y muestra spinner mientras corre; si falla, el texto de esa card pasa a `[Error] ...` sin afectar al resto.
  - **Copiar/descargar todo junto**: botones "Copiar todo" / "Descargar todo" junto a "Volver a empezar" (`combineResultsText` concatena `--- nombre.ext ---\n<texto>` por archivo). Descarga como un solo `.txt` (`textos-reconocidos.txt`), no zip — evita sumar una dependencia de compresión por ahora.
  - Modal de preview: extraído a **`src/components/PreviewModal.tsx`** (componente compartido — se repitió por primera vez en `ImagenABase64.tsx`, ver regla de "patrones únicos"). Props `image: { url, name } | null` + `onClose`. Overlay `fixed inset-0 bg-slate-900/80` (oscuro, para contraste de foto), pero la ventana del modal es **siempre clara** (`bg-white`, sin variante dark — a propósito, un visor de imagen se ve mejor con marco claro sin importar el tema de la app): header solo con `border-b border-emerald-200` (sin relleno, el usuario sacó el `bg-emerald-50` que yo había puesto — más sutil) con el nombre de archivo como título (`text-slate-800`) y botón `X` en `emerald-700`, imagen debajo. Reusar este componente en cualquier tool page nueva que necesite preview de imagen a pantalla completa (no reimplementar inline).
  - Todo elemento clickeable lleva `cursor-pointer` explícito (no asumir el default del navegador en `<button>`).
  - **Motor `fast` (Tesseract.js) implementado** en `src/lib/ocr.ts`:
    - `createOcrWorker()` — worker único `spa+eng`, `OEM.LSTM_ONLY`, con `legacyCore: true, legacyLang: true` (necesario para que `worker.detect()` funcione — ver abajo). Se crea una vez por conversión (no por archivo) y se termina (`worker.terminate()`) al final vía `finally`.
    - `recognizeWithTesseract(worker, file)` — **usa OSD (`worker.detect()`)** para detectar orientación (modelo dedicado y liviano) en vez de probar las 4 rotaciones con reconocimiento completo cada una (heurística anterior, ~3-4x más lenta y menos confiable). `normalizeRotation` redondea `orientation_degrees` al múltiplo de 90 más cercano. 1 sola pasada de `recognize()` en la rotación corregida. Si `detect()` falla, sigue sin rotar en vez de cortar la conversión. Antes de reconocer, aplica `enhanceForOcr` (escala de grises + umbral suave).
    - **Downscaling**: `drawScaled` achica a `MAX_DIMENSION = 2000` px de lado mayor antes de procesar (fotos de celular no ganan precisión pasado ese tamaño, solo tiempo). Se aplica en ambos motores.
    - `handleConvert` en `Ocr.tsx` es async: crea el worker, procesa archivos **uno por uno** (secuencial — un solo worker de Tesseract no gana nada corriendo en paralelo), actualiza `progress` (`done/total`) y muestra spinner (`IconLoader2 animate-spin`) + texto "Reconociendo texto (n/total)..." en el botón mientras `isConverting`.
  - **Motor `ai` (Mistral Pixtral) implementado vía backend propio** (decisión del usuario: backend mínimo, no exponer la key en el cliente):
    - `api/ocr-ai.ts` — función serverless formato **Vercel** (`VercelRequest`/`VercelResponse` de `@vercel/node`, devDependency). Recibe `{ image: string }` (data URL base64) por `POST`, arma un chat completion a `https://api.mistral.ai/v1/chat/completions` con `model: 'pixtral-12b-2409'` y un mensaje con `image_url` + prompt de extracción, usando `process.env.MISTRAL_API_KEY` (sin prefijo `VITE_`, nunca se expone al bundle). Devuelve `{ text }`. **El nombre del modelo y la forma exacta del payload de Mistral no se verificaron contra la doc en vivo — revisar si Mistral cambió algo antes de confiar 100% en esto.**
    - `recognizeWithMistral(file)` en `src/lib/ocr.ts` — achica/comprime la imagen (`drawScaled` + `toDataURL('image/jpeg', 0.85)`) antes de mandarla, para que suba más rápido; si falla ese paso cae a `fileToDataUrl` (sin comprimir) como fallback. Sin `confidence` real de Mistral, se hardcodea `100` (el campo existe por compartir el tipo `OcrResult` con Tesseract, no se usa para nada en el motor IA).
    - **Concurrencia**: a diferencia de `fast` (secuencial), el motor `ai` procesa archivos en paralelo con `mapWithConcurrency` (`AI_CONCURRENCY = 3` en `Ocr.tsx`) — son llamadas de red a un backend, no CPU local, así que sí gana con paralelismo. Si `recognizeWithMistral` tira error en algún archivo (ej. sin backend corriendo), ese resultado puntual muestra `[Error] ...` en vez de romper toda la conversión.
    - **Local**: `pnpm dev` (plain Vite) **no sirve `/api/*`** — hace falta `pnpm dev:vercel` (`vercel dev`, requiere `vercel` CLI, `npx vercel dev` si no está instalada globalmente) para probar el motor IA en desarrollo. El motor `fast` (Tesseract) sí funciona con `pnpm dev` normal, no depende de `api/`.
    - `tsconfig.node.json` incluye `api` además de `vite.config.ts` para que `tsc -b` type-checkee la function (antes solo cubría `src`).

  - **Estimación de tiempo de crackeo** (`estimateCrackTime`, asume 10^10 intentos/seg — ataque offline rápido, estimación conservadora): convierte bits de entropía a segundos y elige la unidad más grande que quepa (segundos → siglos), con singular/plural correcto (`1 hora`, no `1 horas`) y buckets "Miles de .../ Millones de ..." para números muy grandes en vez de mostrar el número exacto.
  - Ícono `IconKey` (ya estaba curado en la lista de íconos para "Contraseñas seguras" desde antes de construirse).
- **`Qr.tsx`** (`/qr`) — generador y lector de QR, 100% client-side. Vuelve al layout **fluido de 2 columnas estilo `Ocr.tsx`** (`grid-cols-1 lg:grid-cols-2 gap-6`, cards simples `border-slate-200 bg-white dark:bg-slate-900`, sin glassmorphism ni dimensiones fijas en px) — a diferencia de `Contrasenas.tsx`, acá no hubo pedido de replicar ningún wireframe con medidas exactas, así que se usó el patrón por defecto de las tool pages (confirma que el patrón "fijo en px + glass" de Contrasenas es la excepción, no la nueva norma).
  - **Librerías nuevas**: `qrcode` (generación, `QRCode.toCanvas`) y `jsqr` (lectura, decodifica `ImageData` a texto) — ambas 100% client-side, sin backend. `@types/qrcode` como devDependency (`jsqr` no necesitó `@types` aparte, compiló bien con sus propios tipos).
  - **Alcance decidido con el usuario antes de construir** (vía `AskUserQuestion`): 4 tipos de contenido — Texto, URL, WiFi (SSID + contraseña + seguridad WPA/WEP/sin contraseña, arma el string `WIFI:T:...;S:...;P:...;;` estándar que el celular reconoce y conecta directo al escanear) y Contacto (vCard simple: nombre/teléfono/email) — se descartó explícitamente sumar email/tel/SMS sueltos y también descartar WiFi/Contacto, quedó el punto medio. Personalización de estilo: **solo color de primer plano y de fondo** (`<input type="color">` nativo) — se descartó explícitamente logo en el centro y esquinas redondeadas por el riesgo de bajar la legibilidad del QR y el esfuerzo extra de implementación.
  - **Dos modos** (mismo pill-toggle "Generar"/"Leer" que Random/Memorable de Contrasenas): en Generar, un selector de 4 botones (Texto/URL/WiFi/Contacto) cambia qué formulario se muestra debajo, todo alimentando un solo string derivado `qrValue` que se dibuja en un `<canvas>` vía `QRCode.toCanvas` en un `useEffect`. Si `qrValue` está vacío (campos sin completar), no se dibuja nada — se muestra un ícono `IconQrcode` grande en gris + "Completa los datos para ver el código QR" en su lugar, mismo espíritu que el estado vacío de "Elige al menos un tipo de carácter" en Contrasenas.
  - **Bug real encontrado (React, no específico de este proyecto) al probar mobile**: el `<canvas>` vive dentro de un bloque condicional (`{mode === 'generate' ? (...) : (...)}`), así que al cambiar a "Leer" y volver a "Generar", React **desmonta y remonta un `<canvas>` nuevo** — pero el `useEffect` que dibuja el QR tenía como deps `[qrValue, fgColor, bgColor]` nada más, así que si esos valores no cambiaron (típico: el usuario solo fue y volvió sin tocar el formulario), el efecto no se re-ejecutaba y el canvas nuevo quedaba en blanco con el tamaño default del navegador (300×150, el tamaño que un `<canvas>` sin atributos `width`/`height` explícitos toma por default — señal útil para reconocer este bug: si un canvas mide justo 300×150, casi seguro nunca se dibujó nada en él). Fix: agregar `mode` al array de deps del efecto, así se re-dibuja cada vez que se vuelve a "Generar". **Lección general**: un `ref` a un elemento dentro de un bloque condicional puede apuntar a un nodo DOM distinto en cada montaje — si un efecto solo depende de "los datos a dibujar" y no de "si el elemento a dibujar existe/cambió", puede quedar desincronizado exactamente en este escenario (condicional + volver atrás sin cambiar los datos).
  - **Lector**: mismo dropzone reusado de Ocr/Base64 (click/drag/paste, `ACCEPTED_TYPES` jpg/png/webp) pero para **un solo archivo** (reemplaza el anterior si se sube otro — a diferencia de Ocr que acumula varios, acá no tiene mucho sentido leer QRs en lote en la misma pantalla). Decodifica con `createImageBitmap` + canvas temporal + `jsQR(imageData.data, width, height)`. Si `jsQR` no encuentra nada, mensaje simple "No se encontró ningún código QR en esa imagen" (sin rojo, mismo criterio ya documentado de no salirse de la paleta Emerald+Slate para errores de texto). Si el contenido decodificado empieza con `http://`/`https://`, aparece un botón extra "Abrir enlace" (`target="_blank" rel="noopener noreferrer"`) además de "Copiar".
  - **Probado con round-trip real** (generar un QR, bajar el PNG del canvas, subirlo al lector) para WiFi y URL — decodifica exacto lo mismo que se generó, confirmado en el navegador, no solo por inspección de código.
  - Contenedor de página `max-w-7xl` — pedido explícito del usuario (2026-08-14) de usar más ancho de pantalla acá; en `/qr` el ancho es fijo siempre (no varía según si hay archivos/resultados, porque el layout de 2 columnas del generador/lector se muestra siempre que se elige un modo, no solo cuando hay datos cargados). Ocr/Base64/Facturas subieron después a este mismo `max-w-7xl` en reposo (ver `## Ancho de contenedor de tool pages`), así que ya no es una excepción de `/qr`.
  - **Pill-toggle "Generar"/"Leer" alineado a la izquierda** (`flex justify-start`, sin `justify-center`) — pedido explícito del usuario (2026-08-17): quedaba centrado en un contenedor `max-w-7xl` bastante ancho, lejos del H1/subtítulo que están a la izquierda, se veía descolgado.
  - **Las 4 cards (2 en Generar, 2 en Leer) comparten la misma altura fija en desktop**: `lg:h-104` (416px, mismo valor que usa `Ocr.tsx` para su dropzone+lista) en las 4 — antes cada modo tenía su propia altura natural (el form de Generar es más alto que el dropzone `min-h-72` de Leer), así que cambiar de pestaña generaba un salto de tamaño de página. Card de config/formulario y card de resultado de Leer llevan `overflow-y-auto` de safety (el formulario "Contacto", con 3 campos, es el contenido más alto y puede acercarse al límite de 416px).

## Sección "Otras herramientas" en cada tool page (congelado, 2026-08-14)

**`src/components/OtherTools.tsx`** — componente compartido, pedido explícito del usuario: toda página de herramienta debe mostrar, al final, una grilla con las demás herramientas disponibles (mismo patrón visual que la sección "Herramientas disponibles" de `Inicio.tsx`: heading `text-2xl font-bold text-emerald-600 sm:text-3xl dark:text-emerald-400` + grid `grid-cols-2 sm:grid-cols-3 lg:grid-cols-4 gap-4` con `ToolCard` y reveal-up escalonado). Recibe `currentHref` y filtra `availableTools` para no mostrarse a sí misma.

**Colocación**: un solo `<OtherTools currentHref="/xxx" />` como sibling *después* de la `<section>` principal de la página (no adentro), envolviendo el `return` en un fragment `<>...</>`. Con esto alcanza una sola inserción por página para cumplir el pedido de "que aparezca tanto en el estado inicial como debajo de los resultados" — como el bloque de resultados y el de formulario/dropzone son ramas condicionales mutuamente excluyentes dentro de la misma `<section>`, `OtherTools` queda siempre como lo último de la página sin importar cuál rama esté activa, sin necesidad de duplicarlo en cada rama. Ancho propio `max-w-7xl` independiente del ancho (a veces dinámico) de la section de la tool. Ya insertado en `Ocr.tsx`, `ImagenABase64.tsx`, `Contrasenas.tsx`, `Qr.tsx`, y en las 3 tools nuevas de abajo — **toda página de tool nueva debe agregarlo también**, es parte del molde estándar junto con `FOCUS_RING`/dropzone/etc.

## Tools nuevas — Comparador, Paleta, Facturas (2026-08-14)

- **`Comparador.tsx`** (`/comparador`) — 100% client-side, usa el paquete `diff` (jsdiff) vía `diffWords`/`diffLines` (sin `@types/diff`: la lib trae sus propios tipos, el stub de `@types` está deprecado y se removió). Layout de referencia `Ocr.tsx` (plano, sin glass): dos textareas (Texto original / Texto nuevo) + toggle "Por palabra"/"Por línea" (mismo pill-toggle de siempre) + botones "Intercambiar" (swap) y "Limpiar". **Reactivo vía `useMemo`** (sin botón "Comparar" — el diff es barato de calcular, mismo espíritu que Contrasenas: no todo tool necesita el flujo de dos pantallas). Resultado: un solo bloque de texto con `<span>` por cada `part` del diff, coloreado con el semáforo ya congelado (agregado = `bg-emerald-100 text-emerald-700`, eliminado = `bg-red-100 text-red-700 line-through`, sin cambios = sin clase) — mismo criterio que el badge de confianza de Ocr y la puntuación de Contrasenas: rojo/verde es semáforo de estado, no acento de marca. Stats de `+N/-M palabras` (o líneas) sumando `part.count` de cada fragmento agregado/eliminado — `count` lo calcula la propia librería, no hace falta contar manualmente. **Verificado el shape exacto de `diffWords`/`diffLines`** corriendo la librería directo en Node (`part.added`, `part.removed`, `part.value`, `part.count`) antes de dar por buena la lógica de stats, ya que no se pudo probar la UI en navegador esta sesión (extensión de Chrome desconectada).
- **`Paleta.tsx`** (`/paleta`) — 100% client-side, **sin dependencia nueva**: cuantización de color manual en `src/lib/palette.ts` (`extractPalette`) en vez de sumar una lib tipo `colorthief`. Algoritmo: `createImageBitmap` + downscale a 150px de lado mayor (mismo criterio de `MAX_DIMENSION` que `ocr.ts`, más rápido y sin perder precisión de color relevante) → recorre pixels del `ImageData`, descarta transparentes (`alpha < 128`) → agrupa cada pixel en un bucket de `Math.floor(canal / 32)` por canal RGB (8 niveles por canal, 512 buckets posibles) sumando los valores reales para poder promediar → ordena buckets por frecuencia y devuelve el promedio de color de los N más frecuentes, con `percentage` = proporción de pixels muestreados que cayeron en ese bucket. Dropzone de un solo archivo (igual patrón que el lector de `Qr.tsx`, reemplaza la imagen anterior si se sube otra), análisis automático al soltar/pegar la imagen (sin botón "Extraer", mismo criterio auto-decode de Qr). Resultado: grid de swatches (bloque de color + hex + %), click en cualquiera copia el hex (ícono cambia a check 1.5s, mismo patrón de confirmación visual del resto del sitio) + botón "Descargar" que baja un `.txt` con hex/rgb/porcentaje de todos los colores.
- **`Facturas.tsx`** (`/facturas`) — el objetivo fundacional del proyecto (ver memoria `project_origin_business_idea`). Único motor: **IA** (Mistral Pixtral vía backend propio) — a diferencia de Ocr, acá no tiene sentido un motor "rápido" tipo Tesseract porque el objetivo es extracción estructurada (JSON), no solo texto plano.
  - **`api/factura-ai.ts`** — mismo patrón que `api/ocr-ai.ts` (`VercelRequest`/`VercelResponse`, `MISTRAL_API_KEY` server-side, nunca expuesta al cliente) pero con un prompt que le pide a Mistral **JSON estructurado** (`fecha`, `monto`, `moneda`, `ruc`, `proveedor`, `numero_comprobante`, `null` si el dato no aparece) y `response_format: { type: 'json_object' }` (modo JSON de Mistral, mismo mecanismo que OpenAI) para que la respuesta sea siempre JSON parseable y no texto libre con el JSON mezclado. El endpoint devuelve `{ raw }` (el string JSON tal cual lo mandó Mistral) — el parseo/validación de campos vive en el cliente (`src/lib/factura.ts`), no en el backend.
  - **`src/lib/factura.ts`** (`extractFacturaData`) — comprime la imagen igual que `recognizeWithMistral` de `ocr.ts` (downscale a 2000px + JPEG 0.85, con fallback a `fileToDataUrl` sin comprimir si falla), llama a `/api/factura-ai`, y parsea el `raw` con `JSON.parse` — si Mistral devolviera algo no parseable (no debería pasar con `response_format: json_object`, pero por las dudas) tira un error explícito en vez de asumir campos vacíos silenciosamente. Normaliza campos faltantes a `null` con `??`.
  - **UI**: mismo patrón de dos pantallas y dropzone multi-archivo de `Ocr.tsx` (`mapWithConcurrency` reusado de `lib/ocr.ts`, `AI_CONCURRENCY = 3`, ya que son llamadas de red). Resultado por archivo: en vez de un textarea de texto libre, una grilla de **6 inputs editables** (uno por campo: Fecha, Monto, Moneda, RUC, Proveedor, N° comprobante) — editables porque la IA puede equivocarse en algún campo puntual y no tiene sentido re-procesar toda la imagen para corregir un dato. Si la extracción de un archivo falla, se muestra un badge rojo con el mensaje de error junto al nombre (mismo criterio que el `[Error]` de Ocr) sin romper el resto del lote. "Descargar todo" exporta **CSV** (no `.txt` como Ocr/Base64) — tiene más sentido para el caso de uso de un contador que necesita importar los datos a una hoja de cálculo; `csvEscape` envuelve en comillas y escapa comillas internas solo si el campo trae coma/comilla/salto de línea.
  - **Validado el prompt/schema JSON contra la API real de Mistral** (imagen de recibo sintética generada con ffmpeg: RUC, fecha, proveedor, N° de comprobante y monto de prueba) — la extracción devolvió los 6 campos exactos y el JSON parseó sin errores en el primer intento. **No se pudo probar el flujo completo en la UI del navegador ni el endpoint `/api/factura-ai` corriendo bajo `vercel dev`** en esta sesión: la extensión de Chrome estaba desconectada, y además `vercel dev` no está tomando `MISTRAL_API_KEY` de `.env.local` en este entorno — el mismo problema ocurre con el endpoint viejo `ocr-ai` (`{"error":"MISTRAL_API_KEY no configurada en el servidor"}` en ambos), así que es un problema de esta sesión de `vercel dev`/entorno local, no algo introducido por este cambio. **Pendiente**: reprobar `pnpm dev:vercel` + subir una factura real desde la UI cuando el entorno lo permita, antes de confiar 100% en el flujo end-to-end (el prompt/parseo en sí ya está confirmado contra la API real de Mistral).

## Ancho de contenedor de tool pages (congelado, 2026-08-17)

**Regla**: el ancho "en reposo" (sin archivos/resultados cargados) de toda tool page debe ser `max-w-7xl`, igual que `OtherTools.tsx` — así el `<h1>`/subtítulo de la tool queda alineado con el borde izquierdo de la grilla "Otras herramientas" que aparece al final de la página. Antes varias tools (`Ocr`, `ImagenABase64`, `Facturas`, `Comparador`, `Paleta`) usaban `max-w-5xl` en reposo mientras `OtherTools` es fijo `max-w-7xl` — como ambos contenedores se centran de forma independiente (`mx-auto`) pero con anchos distintos, sus bordes izquierdos NO coinciden (a más ancho, el contenedor arranca más a la izquierda): con `max-w-5xl` (1024px) vs `max-w-7xl` (1280px) el título quedaba **128px más a la derecha** que la grilla de abajo. Bug real reportado por el usuario comparando screenshots de `/contrasenas` (que por casualidad numérica caía casi alineado) contra `/ocr` (claramente desalineado).

**Estado con archivos/resultados cargados**: las tools que ensanchan el contenedor al cargar archivos (`Ocr`, `ImagenABase64`, `Facturas` — ver `files.length > 0` / `isWide`) suben a `max-w-[90rem]` (1440px) en vez de al viejo `max-w-4/5` (fracción relativa al viewport, no a un valor fijo — en pantallas medianas terminaba siendo MÁS angosto que el `max-w-7xl` de reposo, o sea el contenedor se encogía al cargar archivos en vez de agrandarse, otro bug que se corrigió de paso).

**Excepciones que se mantienen así a propósito**:
- `Contrasenas.tsx` sigue en `max-w-[100rem]` (más ancho, ver `## Estilo/diseño` más arriba) — necesita más aire por el grid de 2 columnas con cards de ancho fijo en px. Su título queda razonablemente cerca del borde de `OtherTools` por la combinación `max-w-[100rem]` + wrapper interno `w-fit`, pero no es una garantía matemática como en las demás — si se vuelve a tocar el ancho de esta página, revalidar contra `OtherTools`.
- `Qr.tsx` ya estaba en `max-w-7xl` desde que se creó, no necesitó cambio.
- La sección del **hero** de `Inicio.tsx` se queda en `max-w-5xl` a propósito (documentado arriba, "el hero se queda en `max-w-5xl`, no tocarlo") — no es una tool page, no aplica esta regla.

Si se crea una tool page nueva, el ancho de reposo por defecto debe ser `max-w-7xl` (no `max-w-5xl` como en versiones viejas de este documento) para que el título salga alineado con `OtherTools` sin tener que pensarlo.
